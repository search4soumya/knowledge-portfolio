What this system is solving

Streaming a movie is mostly moving large, cacheable files to a living room. Choosing the title, personalizing the home screen, and authorizing the device are different problems. Netflix-style designs isolate those control-plane services and push bytes to an Open Connect-like CDN so a recommendation outage does not stop playback.

System blueprint

Microservices are useful when they keep the playback path short. The important architectural choice is which calls are allowed to sit on the path of the next video segment.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Open Connect CDN

This is the data plane. Popular titles are pre-positioned on appliances or caches close to ISPs. The player downloads short segments. Because the files are immutable renditions, caches are simple and cheap. The design goal is that a Saturday-night hit never travels from a single origin to every household. Capacity planning here is about fill, eviction, and peering, not about adding more application servers.

Core concepts in this module

  • Edge caching
  • Content pre-positioning
  • Immutable segments
  • Origin shielding

2. Playback API and auth

Before bytes move, the device must be allowed to watch this title on this account. The playback API issues a short-lived license or token, chooses a CDN set, and records the session. It should not stream the movie itself. Keeping authorization in one place lets you revoke a device, enforce concurrency limits, and change CDN routing without touching every microservice.

Core concepts in this module

  • Short-lived licenses
  • Device limits
  • Session records
  • Token expiry

3. Identity, catalog, and recommendations

These services make the product feel personal, but they have different availability needs. Identity must work to start a session. Catalog can serve a slightly stale title list. Recommendations can fail open to a default row. Treating them as independent microservices is useful only if the client has fallbacks. A chain of synchronous calls from the home screen to every personalization model is the opposite of resilience.

Core concepts in this module

  • Microservices
  • Fallback UX
  • Stale-OK reads
  • Bulkheads

4. Viewing events and origin

Playback telemetry is valuable and dangerous. It should never block the next segment. Events go to a stream for quality metrics, recommendations, and billing. Origin storage holds the source files used to fill caches. The origin is expensive and far away, so only cache misses and new publishes should hit it. Separate the analytics pipeline from the path that keeps the picture moving.

Core concepts in this module

  • Async telemetry
  • Event streams
  • Cache fill
  • Failure isolation

How the modules work together

The client asks identity and playback auth for a license and nearby CDN hosts. Catalog and recommendations help the user choose a title, but once playback starts the player mostly talks to the CDN. Viewing events stream off to the side for ranking and billing. If recommendations fail, the app can show a smaller cached row. If a CDN node is overloaded, the client tries another host. Origin storage is a fallback, not the default path for a popular title.
