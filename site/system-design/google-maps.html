System Design: Google Maps

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Maps combine a static, cacheable picture of the world with a dynamic routing problem. Tiles are versioned images or vectors for each zoom and coordinate. Routing searches a road graph. Traffic updates the weights on that graph without forcing every phone to download a new planet.

System blueprint

Do not rebuild tiles because a highway slowed down. Tiles are geography; traffic is a stream of weights.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Tile service and CDN

The world is cut into tiles at many zoom levels. Each tile is immutable for a map version, which makes CDNs happy. Clients request only what is on screen plus a small prefetch. A new map release is a new version prefix, not an edit in place. Vector tiles move styling to the client; raster tiles are simpler images. Either way, the key is z/x/y plus version.

Core concepts in this module

  • Tile pyramids
  • Immutable versions
  • Viewport fetch
  • CDN cache keys

2. Routing

Routing is a shortest-path search on a graph of road segments. Hierarchical techniques and contraction hierarchies keep city-scale queries fast. Alternate routes are bounded; you do not enumerate every path. Partition graphs so a regional replica can answer without loading the planet into one process. When traffic data is missing, fall back to free-flow speeds.

Core concepts in this module

  • Road graphs
  • Shortest path
  • Graph partitions
  • Bounded alternatives

3. Traffic

Probes from phones and historical averages update edge weights. This is a stream. Publish snapshots or deltas to routing replicas. Do not wait for a perfect global picture; a slightly stale weight is better than no route. Extreme incidents can also trigger reroute pushes to active navigations.

Core concepts in this module

  • Probe streams
  • Weight updates
  • Historical priors
  • Reroute signals

4. Places

Businesses and landmarks live in a geo index with attributes such as hours and category. This is closer to nearby search than to tile rendering. Ranking mixes distance and relevance. Hours can be stale, so show freshness and let the details page re-fetch. Places writes should not block tile reads.

Core concepts in this module

  • Geo documents
  • Distance + relevance
  • Freshness labels
  • Decoupled writes

How the modules work together

The client asks for tiles covering the viewport and, separately, for a route. Tiles come from a versioned pyramid at the edge. Routing loads a graph partition, applies traffic weights, and returns a polyline plus ETA. Places search uses a geo index for businesses. Navigation keeps requesting traffic deltas, not a new set of basemap tiles, as the car moves.
