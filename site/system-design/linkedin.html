What this system is solving

A professional feed is an event-driven ranking system on top of a connection graph. The write is 'someone posted or interacted.' The read is 'show me a small set of items I am likely to care about, without violating privacy.' Kafka-style logs let many consumers reuse the same activity: feed, notifications, search, and analytics.

System blueprint

The graph tells you who could see an item. Ranking tells you who should see it now. Those jobs should not share one synchronous service call.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Activity publisher

This module records the user action and appends an event with a stable ID. The event is the contract. If it is incomplete, every downstream job is wrong. Use an outbox so the database write and the log write do not diverge. The publisher should not rank the feed. Its success metric is durable, ordered, replayable activity.

Core concepts in this module

  • Event outbox
  • Stable event IDs
  • Replay
  • Contract versioning

2. Connection graph service

The graph stores who is connected, who follows whom, and which organizations a person belongs to. Feed and notifications query it, but they should not run unbounded traversals on the request path. Common questions become explicit APIs: first-degree connections, followers of this actor, members of this page. Privacy edges change, so consumers must be able to drop candidates that are no longer allowed.

Core concepts in this module

  • Graph APIs
  • Bounded traversal
  • Privacy edges
  • Membership

3. Candidate generation and ranker

Candidate generation is recall: gather more items than you will show. Ranking is precision: order them. Features include author affinity, recency, and inferred topics. Because models change, store the model version with the score. Ranking is expensive, so do it asynchronously for the next session when you can, and keep a cache of the last good list.

Core concepts in this module

  • Recall vs precision
  • Feature store
  • Model versioning
  • Feed cache

4. Kafka log

The log decouples producers from consumers. Feed builders, notification workers, and metrics can move at different speeds. Offsets make replay possible when a ranker is rewritten. Partition by actor or event type so related activity stays ordered. A log is not a database; consumers still need their own derived stores.

Core concepts in this module

  • Pub/sub log
  • Consumer offsets
  • Partition keys
  • Derived read models

How the modules work together

A post or comment is written and emitted to the log. Candidate generation walks or samples the graph and writes possible feed entries. The ranker scores those entries with features from the feature store. A feed request reads a ranked slice, applies privacy again, and caches it briefly. Notifications and search consume the same log with their own offsets. If ranking is slow, the feed can show a simpler recency list rather than fail.
