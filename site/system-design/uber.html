What this system is solving

Ride matching is a real-time marketplace. Riders want a car now, drivers move continuously, and the system must assign one driver to one trip even when two requests arrive together. The design splits fast-changing location data from durable trip state, then treats dispatch as a serialized decision.

System blueprint

H3-like cells turn a map into buckets you can query. ETA is an estimate built from routing and recent traffic, not a promise stored as truth.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Location ingest

Phones send frequent, noisy GPS points. This module validates, smooths, and writes the latest point into a cell-based index. It should not open a database transaction for every ping. Old points expire so a driver who went offline disappears from search. Because drivers cross city boundaries, the ingest path must handle partition moves without creating two live locations for one vehicle.

Core concepts in this module

  • Geospatial indexing
  • TTL locations
  • Noisy GPS
  • Hot city cells

2. Dispatch

Dispatch is the matcher. It searches nearby cells, applies product rules such as car type or rating, and proposes a driver. Two dispatchers can see the same idle driver, so the assignment must be fenced: a lease, a version number, or a unique active-trip constraint. Dispatch can retry with a larger radius, but it must never leave two confirmed trips on one driver.

Core concepts in this module

  • Matching
  • Leases / fencing
  • Idempotent assign
  • Search radius

3. ETA and routing

ETA combines map distance, live traffic, and pickup walking time. It is used to rank candidates and to set expectations, not to lock a car. Because routing is expensive, dispatch should ask it only for a shortlist. A degraded ETA service should fall back to straight-line time rather than block matching entirely.

Core concepts in this module

  • Routing graphs
  • Traffic signals
  • Approximate ETA
  • Degraded fallback

4. Trip service and trip store

The trip is a state machine: requested, assigned, arriving, in progress, completed, canceled. Payments, receipts, and support all depend on this record. Location pings are not the trip. If the app dies, the store still knows who was assigned. Every transition should be recorded with who caused it so a dispute can be reconstructed.

Core concepts in this module

  • State machine
  • Durable source of truth
  • Compare-and-set
  • Audit trail

How the modules work together

Drivers stream location points into ingest, which updates cells in the geo index. A rider request creates a trip in a requested state. Dispatch queries nearby cells, filters busy drivers, asks routing for ETAs, and attempts to lock one driver. The trip store is the authority: a compare-and-set changes the trip to assigned. Both apps subscribe to trip status. If the driver never accepts, the lease expires and dispatch tries again with a wider radius.
