What this system is solving

A rate limiter is a policy engine in front of expensive work. It answers whether this caller may proceed now. The algorithm you pick encodes the product rule: token bucket allows bursts, sliding window smooths traffic, fixed window is simple and slightly unfair at boundaries. In a fleet of gateways the hard part is shared state and failure policy.

System blueprint

If the limiter store is down you must choose fail-open or fail-closed. That choice is part of the design, not an afterthought.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Identity

Limits are meaningless if the key is wrong. Anonymous traffic uses IP and TLS fingerprints with care; authenticated traffic uses the user or API key. Expensive routes get their own key suffix so a cheap health check does not share budget with an export job. Identity must be cheap; a limiter that calls a remote user service on every request becomes the outage.

Core concepts in this module

  • Caller keys
  • Route-specific budgets
  • Cheap identification
  • Multi-tenant fairness

2. Limiter decision

This module implements the algorithm. Token bucket stores a balance and a last refill time. Sliding window stores counts in time slots. The update must be atomic across gateways, usually with Redis-style scripts or compare-and-set. Return a retry-after with jitter so rejected clients do not retry in lockstep. Document what happens when this module cannot reach the store.

Core concepts in this module

  • Token bucket
  • Sliding window
  • Atomic counters
  • Jittered retry-after

3. Policy config

Policies change without a redeploy: 100 requests per minute for free users, 10 per second for search, a temporary ban. Store them in a small config with versions. Operators need an emergency switch. Keep the number of policies small enough that every request does not evaluate a novel.

Core concepts in this module

  • Versioned policies
  • Emergency kill switch
  • Per-tier limits
  • Composable rules

4. Counter store and metrics

State is tiny and extremely hot. Use memory-speed storage with replication and short TTLs so dead keys vanish. Metrics should show reject rate by key class, not only totals, or you will miss a single abusive tenant. Do not log every decision at full cardinality; sample.

Core concepts in this module

  • Distributed counters
  • Hot-key storage
  • TTL hygiene
  • Reject metrics

How the modules work together

The gateway extracts a key such as user, API token, or IP. The decision module reads policy, performs an atomic increment or token consume, and returns allow or retry-after. Metrics record both results. The application runs only on allow. Policies can stack: a global IP limit and a tighter limit on the search endpoint. Clock sources must be server-side so clients cannot reset their budget.
