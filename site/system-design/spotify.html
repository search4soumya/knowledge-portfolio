System Design: Spotify

What this system is solving

Music streaming looks like video streaming with smaller files and a stronger catalog of user-made playlists. Playback should work even if the recommendation model is unhappy. Audio segments are cacheable. Playlist edits are metadata. Listening history is an event stream that later trains recommendations.

System blueprint

A skipped song is an event, not a reason to stall the next segment.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. License token and playback API

Rights differ by country, device, and subscription. This module issues a short-lived token that the CDN or player can verify. It is also where offline download grants are recorded. Keep it independent from recommendation so billing and licensing outages are visible and rare, not tangled with a model release.

Core concepts in this module

  • Entitlement
  • Short-lived tokens
  • Territory rules
  • Offline grants

2. Audio CDN

Tracks are encoded at a few bitrates and stored as objects. Popular tracks should already be at the edge. The player can switch bitrate between segments. Because tracks are smaller than movies, caching is easier, but catalog size is huge; not everything can be hot. Origin fill and popularity-based prewarm still matter.

Core concepts in this module

  • Multi-bitrate audio
  • Edge cache
  • Popularity prewarm
  • Segment fetch

3. Playlists

A playlist is an ordered list of track IDs with collaborators and a version. Concurrent edits need a version check or CRDT-like list if many people edit at once. The playlist is not the audio. Sharing a playlist shares metadata and entitlements, not a zip of files.

Core concepts in this module

  • Ordered lists
  • Collaborative versions
  • Track pointers
  • Cache of playlist JSON

4. Recommendations and listen stream

Every play, skip, and completion is an event. Pipelines build features and candidate lists. The online service should read prepared rankings and apply a few rules, not train a model on the request. Deduplicate events so a retried client does not convince you someone looped a track 400 times.

Core concepts in this module

  • Listen events
  • Nearline features
  • Prepared rankings
  • Event dedup

How the modules work together

The player asks for a license and a list of CDN hosts, then fetches encrypted segments. Playlist changes update the playlist database and invalidate a small cache. Listens go to a stream used for history and models. Recommendations compute offline and nearline; the home screen reads a prepared list. If recommendations fail, recently played and downloaded titles still work.
