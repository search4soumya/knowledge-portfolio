What this system is solving

File sync is a metadata problem dressed as a storage problem. The bytes can be split, hashed, and stored once. The hard work is reconciling trees across devices: renames, offline edits, deletes, and two people changing the same file. The blueprint stores chunks immutably and lets a metadata service decide what the current tree is.

System blueprint

Dedup is a storage optimization. Sync correctness comes from manifests, versions, and conflict rules, not from hashing alone.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Chunker and dedup

Files are split into chunks so a small edit does not re-upload a 2 GB video. Content hashes let the server skip bytes it already stores. Chunk size is a trade: tiny chunks increase metadata, huge chunks waste upload. Clients should encrypt or hash in a way that still allows the server to address chunks. This module must treat two identical PDFs from different users carefully if privacy requires per-namespace encryption.

Core concepts in this module

  • Content-defined chunking
  • Hash addressing
  • Upload resume
  • Namespace privacy

2. Sync engine and metadata

Metadata holds paths, permissions, versions, and the list of chunk hashes that make a file. Commits are transactional: a new tree either replaces the old one or is rejected as stale. Renames are metadata operations, not byte copies. Sharing a folder is an ACL change on a subtree, which is why metadata, not object storage, is the product database.

Core concepts in this module

  • Manifest commit
  • Optimistic versions
  • Rename as metadata
  • ACLs on trees

3. Notification service

Devices should not poll every few seconds. After a commit, this module wakes subscribed clients with a cursor. The client then fetches the delta. Notifications can be lossy if the cursor protocol is correct: a missed ping just means a later catch-up. This is cheaper and kinder to batteries than tight polling.

Core concepts in this module

  • Change notifications
  • Device cursors
  • Lossy ping, reliable delta
  • Wake vs poll

4. Chunk store and device cursors

The chunk store is append-only object storage. Device cursors remember how far each client has applied the tree. Tombstones record deletes so a device that was offline does not resurrect a file. Garbage collection is delayed and reference-counted. If you delete bytes when the first user removes a file, you may destroy a chunk another namespace still needs.

Core concepts in this module

  • Immutable chunks
  • Tombstones
  • Reference counting
  • Delayed GC

How the modules work together

A client hashes local chunks, asks which hashes the server already has, uploads the missing ones, and commits a new manifest for the file path. The metadata service assigns a version and notifies other devices. Those devices download missing chunks and apply the tree change. If two commits descend from the same parent, the service keeps a conflict copy instead of silently choosing. Garbage collection waits until no manifest references a chunk.
