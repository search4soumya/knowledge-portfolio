System Design: Ticketmaster / BookMyShow

What this system is solving

Ticketing is inventory under a flash sale. Many people want the same seats at the same instant. The browser cannot own a seat. A hold is a short lease in a transactional inventory service, and payment is a later step that must not create a second sale if the client retries. An admission queue protects the database from becoming the waiting room.

System blueprint

If two checkouts can both mark seat A12 sold, the rest of the architecture does not matter. Start from a unique constraint or conditional update on the seat.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Waiting room

This is load management, not shopping. It issues a signed token when a browser may enter checkout. The release rate matches inventory and payment capacity. Without it, you scale the storefront into a self-inflicted outage. The waiting room should be simple and separately scalable: it does not browse every seat map.

Core concepts in this module

  • Admission control
  • Signed entry tokens
  • Release rate
  • Flash-sale shedding

2. Inventory and seat lock

Each seat has a state: available, held, sold. A hold writes who owns it and when it expires. The write uses a condition so only one holder wins. Holds are short because abandoned browsers are common. Extending a hold is an explicit call, not an infinite reservation. Seat maps can be cached for display, but the lock always goes to the authority.

Core concepts in this module

  • Conditional updates
  • Short leases
  • Cached map, authoritative lock
  • Expiry workers

3. Payment and order service

Payment is slow and retries. The order record must survive a double callback. Convert hold to sold only after the processor confirms, and store the processor reference. The user-visible confirmation is derived from order state, not from the last browser response. This is a small saga: hold, charge, sell, or compensate.

Core concepts in this module

  • Idempotent payment
  • Order state machine
  • Compensation
  • Webhook races

How the modules work together

Users receive a place in the waiting room and are admitted at a rate the core can handle. Selecting seats creates a hold with an expiry. Payment uses an idempotency key. On success the order service converts the hold to sold. A sweeper releases expired holds. If payment succeeds after the hold expired, reconciliation must either restore the seat sale or refund; it must not silently drop the money.
