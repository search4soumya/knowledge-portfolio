What this system is solving

Retail checkout is a long-running workflow across catalog, cart, inventory, payment, and fulfillment. No single database transaction spans the warehouse and the card network. The order becomes a saga: a durable state machine with steps and compensations. Inventory is reserved, not guessed from a cached count on the product page.

System blueprint

A sold-out badge on the storefront is a hint. The reservation at checkout is the decision.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Cart

The cart is a working document. It survives devices through an account ID or a signed cookie. It can hold items that later go out of stock. Do not put payment authorization in the cart. Price the cart at checkout time because promotions change. Merge guest and user carts carefully to avoid losing items or leaking another person's basket.

Core concepts in this module

  • Durable intent
  • Price at checkout
  • Cart merge
  • No hard reservation

2. Inventory

Inventory is a ledger of on-hand, reserved, and shipped units per SKU and location. Reservations use conditional decrements. Oversell happens when you decrement a cache. Multi-warehouse routing is a later choice; correctness starts with one atomic reservation record. Expired reservations return stock to the pool.

Core concepts in this module

  • Reservation ledger
  • Conditional decrement
  • Reservation TTL
  • Location-level stock

3. Order workflow

The order ID is the customer's handle on the saga. States include created, paid, allocated, shipped, and canceled. Each step records a command result so retries do not charge twice or ship twice. An outbox publishes events for email, fraud, and warehouse systems. Humans in support need the same state machine; they should not edit stock by folklore.

Core concepts in this module

  • Sagas
  • Order state machine
  • Outbox events
  • Compensation

4. Payment and fulfillment

Payment talks to a processor with idempotency keys. Fulfillment assigns warehouses, packing, and carriers. These modules should accept commands from the order workflow, not invent their own order IDs. Tracking numbers flow back as events. Partial shipment is a first-class state, not an exception buried in notes.

Core concepts in this module

  • Idempotent capture
  • Warehouse allocation
  • Partial shipment
  • Event callbacks

How the modules work together

Browsing hits cached catalog. Adding to cart writes intent, often without a hard reservation. Checkout creates an order, reserves stock, authorizes payment, and emits events. Fulfillment allocates a warehouse and later ships. If payment fails, reservations release. If an item cannot ship, compensation refunds or splits the order. The customer sees order state derived from the log, not from whatever page they last posted.
