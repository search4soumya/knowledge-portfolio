System Design: Notification service

What this system is solving

Notifications look like 'send a message,' but the system is a router across push, email, and SMS with preferences, priority, and limited retries. The product emits an intent. Channel workers talk to vendors. A user who opted out of marketing must still receive a security code. Those are different pipelines, not a boolean.

System blueprint

A notification is not sent until preferences, templates, and idempotency keys say it should be. Vendors fail; your attempt log is the memory.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Notify API and router

The API accepts an intent, not a raw vendor payload. The router chooses channels, drops opted-out marketing, and enforces a dedup key so a retried order event does not SMS twice. Priority selects a queue. This is also where you reject unknown templates before they become poison pills in workers.

Core concepts in this module

  • Intent vs send
  • Dedup keys
  • Preference checks
  • Priority queues

2. Templates

Templates keep copy and layout out of every microservice. They need versioning, locale, and a strict variable schema so a missing name cannot produce 'Hello {user}'. Render here, not in each worker, so email and push stay consistent. Preview in staging is part of safety.

Core concepts in this module

  • Versioned templates
  • Locales
  • Strict variables
  • Preview

3. Channel workers

One worker pool per vendor isolates timeouts. SMS outages should not block push. Workers record provider message IDs. Retries use exponential backoff and a maximum. Permanent errors such as invalid number go to a suppression list. Rate-limit yourself to stay under vendor caps.

Core concepts in this module

  • Per-vendor isolation
  • Backoff
  • Suppression lists
  • Vendor rate caps

4. Preferences and attempt log

Preferences are the user's contract. Attempt logs are yours: what you tried, when, and why it stopped. They power support and compliance. Retention should be long enough to debug and short enough to respect privacy. Do not use the attempt log as a marketing analytics warehouse without a plan.

Core concepts in this module

  • Opt-in / opt-out
  • Audit of sends
  • Retention
  • Support traces

How the modules work together

A service posts an intent: user, template, priority, dedup key. The router checks preferences and quiet hours, renders a template, and enqueues one or more channel jobs. Workers call vendors and record attempts. Temporary failures retry with backoff; permanent failures stop. Security messages use a separate queue so a marketing blast cannot starve them. The original service can poll or subscribe to delivery state if it must.
