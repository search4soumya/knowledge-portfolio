System Design: Web crawler

What this system is solving

A crawler is a distributed scheduler that downloads the web without becoming a denial-of-service tool. The frontier decides what to fetch next. Politeness limits how hard you hit one host. Dedup stops you from fetching the same page through a thousand URLs. Workers are replaceable; the frontier and seen-set are the system.

System blueprint

If you only remember one rule, remember per-host concurrency. Throughput without politeness is just abuse.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. URL frontier

The frontier is a prioritized, partitioned queue of work. Priority might be site importance, recency, or change rate. Partition by host so one site cannot occupy every worker. Leases prevent two fetchers from taking the same URL. When a worker dies, the lease expires and the URL returns. This is the difference between a queue and a lost-work pile.

Core concepts in this module

  • Prioritized queues
  • Host partitions
  • Work leases
  • Replay on timeout

2. Politeness

Politeness reads robots.txt, crawl-delay, and your own per-host QPS budget. It is a gate in front of the fetcher, not a comment in a design doc. Some hosts need even stricter limits after errors. Identify your crawler honestly. Ignore this module and you will be banned, sued, or both, and your data will be biased toward whoever failed to block you.

Core concepts in this module

  • robots.txt
  • Per-host QPS
  • Backoff on errors
  • Honest user-agent

3. Dedup and parser

Canonicalization strips tracking query params and session IDs before hashing. Dedup can use an exact store for recent URLs and a Bloom filter for the long tail. The parser extracts links and language, and it must bound HTML size so a huge page cannot explode memory. Content hashes detect that two URLs are the same document.

Core concepts in this module

  • URL canonicalization
  • Bloom filters
  • Content hashes
  • Bounded parse

4. Fetcher fleet and content store

Fetchers are stateless HTTP clients with timeouts, size limits, and sandboxing. They write raw content and fetch metadata: status, headers, time. The store is append-oriented so you can recrawl and keep history. Do not run JavaScript in the fetcher unless you have an isolated renderer farm; that is a different, more expensive module.

Core concepts in this module

  • Timeouts and size caps
  • Stateless workers
  • Fetch metadata
  • Optional render farm

How the modules work together

Operators load seeds. The frontier leases URLs to fetchers that respect robots rules and host budgets. Successful fetches go to content storage and to a parser. The parser extracts links, canonicalizes them, and asks dedup whether each URL is new. New URLs re-enter the frontier with a priority. Failures retry with backoff or go to a dead-letter queue. The seen index must be huge and approximate-tolerant; a rare re-fetch is better than unbounded growth.
