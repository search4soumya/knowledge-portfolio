What this system is solving

Marketplace lodging has a soft search problem and a hard booking problem. Search can be a little stale. A double-booked apartment cannot. Availability calendars, ranking, and payments therefore live in different modules, and the booking path re-validates dates against a transactional store even if search showed the listing as open.

System blueprint

Think of search as advertising and booking as inventory. The advertisement can lag; the inventory cannot.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Search ranking

Ranking mixes quality, price, location, and business goals. It reads a denormalized listing index, not the reservation table. That keeps search fast and independently scalable. Because the index lags, the UI should treat results as candidates. Filters such as 'entire home' belong in the index; 'available these exact dates' should be rechecked at booking even if also used as a search filter.

Core concepts in this module

  • Denormalized index
  • Multi-signal ranking
  • Stale availability
  • Candidate vs commit

2. Calendar

The calendar captures host rules: min stay, blocked dates, preparation time. It is the input to availability, not the reservation itself. Modeling this as per-listing date rows or ranges is a product choice with different update costs. Calendar edits must not silently erase existing reservations; they only change what new guests can book.

Core concepts in this module

  • Availability rules
  • Range vs per-day rows
  • Host constraints
  • Non-destructive edits

3. Booking service

Booking inserts a reservation with a constraint that prevents overlapping stays, or it locks the listing dates in a transaction. It then starts payment as a saga. The guest receives a reservation ID immediately. Everything else—emails, search updates, host payouts—follows from events. Two guests clicking the same weekend is the race this module exists to win exactly once.

Core concepts in this module

  • Exclusion constraints
  • Booking saga
  • Reservation ID
  • Race to lock

4. Payments

Money may be authorized at request and captured after host acceptance, depending on the product. Payouts to hosts are delayed on purpose. Each movement needs a ledger entry and an idempotency key. Booking state and payment state can disagree briefly; a reconciler, not the guest refresh button, fixes that.

Core concepts in this module

  • Auth vs capture
  • Idempotency
  • Delayed payouts
  • Reconciliation

How the modules work together

Hosts publish listings and calendar rules. An indexer builds documents for search. Guests query ranking, then start a booking. Booking locks the date range, starts payment, and commits a reservation. Events update the search document so the listing disappears for those nights. If payment fails, the lock expires. Host cancellations and guest cancellations are explicit transitions with refund rules, not deletes of history.
