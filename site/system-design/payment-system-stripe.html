System Design: Payment system (Stripe)

Beginner-friendly case studies that explain how familiar systems work, what they optimize, and where their designs fail.

What this system teaches

Payment system (Stripe) is a useful case study because it turns a familiar product into a set of engineering decisions. Start with the user action, identify the data that must survive, and then decide which work can happen later.

  • Idempotency — safely retry payment requests
  • Ledgers — record money movement
  • Reconciliation — compare independent records
  • Webhooks — notify merchants asynchronously

How a request moves

A merchant submits a payment with an idempotency key. The payment service validates it, calls a processor, records an immutable attempt and ledger entries, and returns a stable result. Webhooks notify the merchant and reconciliation jobs compare processor reports.

A beginner-friendly design

Treat the ledger as append-only and derive balances from entries. Store the idempotency key with the final response. Model authorization, capture, refund, and dispute as separate states. Never use a mutable balance as the only audit trail.

Data, scale, and consistency

Keep the first version simple: separate the request path from background work, measure the slowest dependency, and store an identifier that makes retries safe. Add replicas and caches only after the access pattern is visible. Decide which values may be briefly stale and which action must be serialized, such as a payment or seat reservation.

What can go wrong

Networks time out after the processor accepts a charge, webhooks arrive twice or out of order, and settlement totals can differ. Use idempotent handlers, signed events, retry queues, and human-visible reconciliation reports.

Key takeaway: Money systems need an auditable history and safe retries more than clever request throughput.
