System Design: WhatsApp

What this system is solving

Chat feels instantaneous, but the network is not. People switch from wifi to mobile, lose signal in elevators, and expect a message that left their phone to arrive later. A WhatsApp-style system is a connection fabric plus durable per-device queues. Presence and typing are hints; message history is truth.

System blueprint

Erlang-style designs shine here because each connection can be a lightweight process. The architectural lesson is more general: isolate connections from durable delivery.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Connection gateway

This module holds millions of sockets. It authenticates a device, keeps a session, and forwards bytes to the router. It should store as little durable state as possible so you can add or restart gateways. When a phone reconnects, the gateway helps the client resume from a cursor rather than replaying the entire history. Health checks must distinguish 'process up' from 'can still push messages'.

Core concepts in this module

  • Long-lived connections
  • Session resume
  • Horizontal gateways
  • Backpressure

2. Message router

The router is the delivery brain. It looks up devices for a user, writes the message once, and places work on each device queue. It does not need the plaintext if end-to-end encryption is in use; it routes envelopes. Ordering is per conversation, not global. Fan-out to a large group should be asynchronous so the sender is not blocked on the slowest member.

Core concepts in this module

  • Per-device queues
  • Envelope routing
  • Conversation ordering
  • Group fan-out

3. Receipt and presence services

Delivery and read receipts are themselves messages with a small payload. They must be idempotent because acks are retried. Presence is a TTL map: last seen, or a short 'online' flag. Mixing presence into the durable message table wastes writes and creates false precision. Users understand 'last seen recently' better than a blinking lie.

Core concepts in this module

  • Idempotent acks
  • Read receipts
  • TTL presence
  • Eventual status

4. Message store and offline queues

The store keeps conversation history and media pointers. Offline queues keep what has not been acknowledged by a device. Those are different retention rules. A queue can drop a payload after the device acknowledges; the store may keep it for new-device linking depending on the product. Encryption and multi-device pairing constrain what the server is allowed to read or re-encrypt.

Core concepts in this module

  • Durable history
  • Ack-based deletion
  • Multi-device
  • Media pointers

How the modules work together

A sender uploads an encrypted payload to its gateway. The router persists the message and enqueues it for each recipient device. If the device is connected, the gateway pushes it immediately and waits for a delivery ack. If not, the offline queue holds it. Read receipts are separate events so a lost ack does not resend forever. Presence updates expire quickly and are not written as permanent rows for every blink of connectivity.
