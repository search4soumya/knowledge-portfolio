What this system is solving

Video is a two-sided system: creators upload large files that must be processed, and viewers stream those files from a nearby edge with changing network quality. The upload cannot live inside a single application server, and the playback path cannot depend on a long chain of business services. The blueprint therefore splits an asynchronous media pipeline from a cacheable playback path.

System blueprint

Original bytes are immutable. Derived renditions are produced by workers and published only when complete. The player never downloads one giant file; it reads a manifest and small segments.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Upload session

Large files fail if you ask the browser to POST once. A session issues an upload ID, accepts chunks, records offsets, and lets the client resume. Integrity checks belong here so a retry does not create a second video. When the last chunk arrives, this module writes a completion event instead of transcoding inline. That keeps user-facing latency predictable and isolates a slow encoder from the upload API.

Core concepts in this module

  • Resumable upload
  • Chunk checksums
  • Idempotent commit
  • Direct-to-storage

2. Transcoder farm

Raw uploads are the wrong shape for phones, TVs, and poor networks. Workers read the original, produce several resolutions and codecs, package segments, and write a manifest. Jobs are pulled from a durable queue so a crashed worker does not lose the video. Outputs should be written to new keys and published atomically. Never overwrite the original; it is the only way to retry or re-encode later.

Core concepts in this module

  • Transcoding
  • Job queues
  • Immutable outputs
  • Atomic publish

3. Catalog

The catalog is the product database: title, owner, visibility, processing state, and pointers to manifests. It is not the video file. Viewers and search read this metadata. A video that is still processing must not appear as ready. Privacy and takedown checks belong here so a CDN URL is not enough to watch a private upload.

Core concepts in this module

  • Metadata vs blob
  • State machine
  • Authorization
  • Eventual listing

4. Playback service and CDN

Playback should be a short control-plane call plus a data-plane fetch. The service authorizes the viewer and returns a manifest location, often with a signed URL. The CDN holds popular segments near the user. Adaptive bitrate is a player behavior: it measures buffer and bandwidth, then picks the next segment. If catalog or recommendations are down, an already authorized stream should still play.

Core concepts in this module

  • Signed URLs
  • CDN caching
  • Adaptive bitrate
  • Control vs data plane

5. Object storage, metadata, and jobs

Object storage keeps originals and renditions. The metadata database keeps product state. The job queue keeps work that may take minutes. These three fail differently: storage needs durability and lifecycle rules, metadata needs transactional state changes, and the queue needs retries without duplicate published videos. A consistent naming scheme for object keys makes cleanup and republish possible.

Core concepts in this module

  • Object immutability
  • Lifecycle policies
  • At-least-once jobs
  • Key design

How the modules work together

A creator starts a resumable upload session, sends chunks to object storage, and commits. The catalog records a processing video and a worker queue receives a job. Transcoders produce renditions and a manifest. Only then does the catalog mark the video playable. A viewer asks the playback service for an authorized manifest URL; the player fetches segments from the CDN and switches bitrate as the buffer changes. Failed transcodes retry from the original object, not from a half-written output.
