System Design: Instagram

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Photo sharing combines a social graph, a media pipeline, and a feed. The image bytes are large and cacheable. The metadata is small and frequently queried. IDs must be unique across shards and roughly sortable by time so feeds can page without asking every shard for 'latest.'

System blueprint

Sharding is usually by user. That makes 'posts by this author' easy and 'global latest' hard, which is the right trade if the product is a personal feed.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Media pipeline

This worker turns an original into thumbnails and display sizes. It should be asynchronous so the upload API returns quickly. Variants use new keys so a retry cannot serve a half-resized image. Strip GPS and other sensitive metadata unless the product explicitly keeps it. Failures retry from the original object.

Core concepts in this module

  • Async derivatives
  • Immutable variants
  • EXIF hygiene
  • Retry from original

2. Feed service

The feed is a list of post IDs plus enough author data to render a cell. It can be precomputed for active users or merged at read time for sparse graphs. Celebrity fan-out has the same push/pull tension as Twitter. Authorization is rechecked on read because a switched account from public to private should not keep appearing in caches.

Core concepts in this module

  • Inbox vs fan-in
  • Post pointers
  • Rechecked privacy
  • Active-user materialization

3. ID generator

A good photo ID is unique, compact, and roughly increasing with time. Snowflake-style IDs encode a timestamp and a machine identity so shards can generate IDs without a central lock. Random UUIDs work for uniqueness but make 'give me newer than X' clumsy and fragment indexes. The generator must survive clock skew and process restarts without collisions.

Core concepts in this module

  • Snowflake IDs
  • Time-sortable keys
  • Allocation ranges
  • Clock safety

4. Metadata shards and object storage

User-sharded metadata keeps an author's posts together. Object storage and the CDN carry the bytes. The follow graph decides feed membership. Cross-shard operations, such as a global report or a celebrity lookup, need their own access path. Plan how you will move a user when a shard overheats; that is harder than picking the first hash function.

Core concepts in this module

  • User sharding
  • Object + CDN
  • Hot users
  • Resharding

How the modules work together

The client uploads bytes to object storage, then calls the API with the object key. The ID generator issues a time-sortable ID. Metadata is written to the author's shard. The media pipeline creates thumbnails and a CDN-friendly variant. Feed delivery either pushes the post ID to follower inboxes or pulls recent posts from followed authors at read time. Deleted or hidden media must invalidate CDN paths, not only the metadata row.
