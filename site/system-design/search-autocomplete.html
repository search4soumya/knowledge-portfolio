System Design: Search autocomplete

What this system is solving

Autocomplete must answer in a few tens of milliseconds as a person types. That rules out a general search of the catalog on every keystroke. The system keeps a compact prefix index in memory, a small top-K list per prefix, and a cache for the hottest prefixes. Freshness is handled by rebuilding versions offline.

System blueprint

The online path only reads. Writers publish a new immutable index and flip a pointer.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Suggest API and cache

This path is latency-critical. Cap prefix length, result count, and payload size. Cache full responses for popular prefixes such as 'a' or 'app' with a short TTL. The API should be read-only and cheap to clone in every region. Language and market belong in the cache key or you will suggest the wrong store.

Core concepts in this module

  • Tight SLIs
  • Prefix cache
  • Locale keys
  • Result caps

2. Trie / FST lookup

A trie or finite-state transducer maps a prefix to a small set of completions in memory. This is why autocomplete is fast. The structure is built offline because updating a huge trie in place on the request path is painful. Compact representations matter; the whole hot index should fit in RAM on each replica.

Core concepts in this module

  • Tries
  • Finite-state indexes
  • Memory residency
  • Immutable versions

3. Top-K ranker

Many words share a prefix. You return only a handful. Ranking uses frequency, click-through, recency, and business rules. Safety filters remove spam and offensive completions. Personalization, if any, must be a cheap re-rank of a tiny list, not a new index walk.

Core concepts in this module

  • Top-K
  • Frequency signals
  • Safety filters
  • Light personalization

4. Index builder

Batch jobs read query logs and catalog titles, clean them, and emit a new index artifact. Building is expensive and can fail; never mutate the live structure halfway. Atomic swap keeps the online path simple. Keep one previous version for rollback when a bad dictionary ships.

Core concepts in this module

  • Offline build
  • Atomic swap
  • Rollback version
  • Log-derived dictionaries

How the modules work together

The client debounces slightly and sends the current prefix. The API checks a tiny cache, then queries the in-memory index for completions. A ranker orders them by frequency, freshness, and safety. Offline, query logs and catalog changes build the next index version. A process loads the new version and then serves it. Bad terms are filtered before they ever reach the client.
