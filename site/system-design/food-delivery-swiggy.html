System Design: Food delivery (Swiggy)

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Food delivery coordinates three parties who do not share a process: customer, restaurant, and rider. The order is a state machine. Kitchen time and travel time are estimates that change. Assignment is a smaller version of ride dispatch, with the extra constraint that food is cooling on a counter.

System blueprint

The customer app should read order state, not compute it from independent restaurant and rider APIs.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Order lifecycle

This is the product database: placed, accepted, preparing, assigned, picked up, delivered, canceled. Every other module emits events; this module decides whether the transition is legal. Support tools should replay this log. Do not delete a canceled order; you need it for refunds and disputes. Timeouts matter: an unaccepted order cannot sit forever.

Core concepts in this module

  • Shared state machine
  • Legal transitions
  • Timeouts
  • Support replay

2. Kitchen / restaurant

Restaurants accept, reject, and update prep time. Their systems are unreliable, so the app or a tablet POS should use idempotent commands. Menu and item availability belong here and should flow to the customer catalog asynchronously. A restaurant going offline mid-order is a first-class event, not an error string.

Core concepts in this module

  • Accept / reject
  • Prep-time signals
  • Menu availability
  • Partner unreliability

3. Dispatch and rider geo

Assignment looks like Uber: geo cells, short leases, one rider one order (or a planned batch). Food adds stacking rules and pickup windows. A rider who accepts but never moves must be reassigned. Keep location data hot and the assignment durable on the order.

Core concepts in this module

  • Geo matching
  • Assignment leases
  • Batching rules
  • Reassignment timers

4. ETA and payments

ETA is kitchen remaining plus travel, with uncertainty. Show a range when inputs are poor. Payments usually authorize up front and capture on success, with refunds on cancel. Promos and delivery fees belong on the order, not only on a receipt PDF. Do not let the rider app invent prices.

Core concepts in this module

  • Composite ETA
  • Uncertainty ranges
  • Auth / capture / refund
  • Priced on the order

How the modules work together

A customer places an order and pays. The restaurant accepts and later marks food ready. Dispatch searches nearby riders and leases one. Rider location updates refresh ETA. If the restaurant rejects or the rider vanishes, the order service transitions and may reassign or cancel with a refund. Notifications are derived from those transitions so the three apps do not invent conflicting stories.
