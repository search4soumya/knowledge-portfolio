What this system is solving

A social network is a graph of objects and associations: people, pages, posts, likes, memberships. Most product screens are a few named traversals, not arbitrary graph queries. TAO-style systems put a cache-aware graph layer in front of storage so 'friends of this user' stays fast while still having a durable backend.

System blueprint

Design the API around associations you will actually query. A general graph database query language on the request path is usually the wrong starting point for this product.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Graph API

This is the product contract: get object, get associations, create edge, delete edge. It enforces authentication and privacy, paginates large edge lists, and hides storage layout. If every app writes SQL against the edge table, you will never change sharding. Keep result sizes bounded; 'all friends of friends' is a request you should refuse or precompute.

Core concepts in this module

  • Named traversals
  • Privacy checks
  • Bounded pagination
  • API as facade

2. TAO-style cache layer

TAO popularized a two-level approach: a cache that understands objects and associations, backed by a sharded store. Reads go to the cache; writes go to storage and then invalidate. The cache is not just Redis-as-blob. It knows the graph operations, so it can serve 'assoc get' without assembling a response from many keys in the client.

Core concepts in this module

  • Association cache
  • Read-heavy graph
  • Write-through / invalidate
  • Hot objects

3. Association service and stores

Objects have a type and payload. Edges have a type, from-id, to-id, and time. Storage is sharded so a popular object's edges can be split. Secondary indexes support lookups in the reverse direction, such as 'pages this user likes.' Consistency matters most for privacy edges: a removed friend should not keep seeing cached content.

Core concepts in this module

  • Object/edge model
  • Reverse indexes
  • Sharded edge lists
  • Privacy consistency

4. Invalidation bus

After a write, caches must learn that an edge changed. A lightweight invalidation message is usually better than pushing full objects everywhere. Consumers drop or reload one association list. If invalidations are lost, a TTL remains as a safety net. Version numbers help a reader detect that a cached edge list is older than a write it just performed.

Core concepts in this module

  • Cache invalidation
  • Version tokens
  • TTL safety net
  • Lost-update protection

How the modules work together

A product request asks for an object and a typed edge list, such as members or reactions. The cache layer returns hot data and fills from storage on miss. Writes update storage, then publish invalidations so caches drop or version the changed edges. Privacy is applied at the graph API, not only in the client. Popular objects, such as a major page, need extra caching and careful write batching to avoid a hot partition.
