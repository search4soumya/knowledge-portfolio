System Design: Pastebin

What this system is solving

Pastebin is a small object store with public links, expiry, and a read-heavy traffic shape. Anyone can upload text; anyone with the link may read it. That combination makes abuse, accidental secrets, and sudden popularity the real design constraints. The body lives in object storage. Metadata answers whether the paste still exists and who may see it.

System blueprint

Expiry is both cleanup and authorization. A paste past its deadline must not be readable even if the blob is still on disk for a few minutes.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Paste service

This module issues IDs, enforces size limits, and stores metadata. Unlisted pastes rely on unguessable IDs; private pastes need a real owner check. Rendering must escape HTML so a paste cannot become a script on your domain. The service should not scan the entire object store to list a user's pastes; that is why metadata exists.

Core concepts in this module

  • Unguessable IDs
  • Size limits
  • Safe rendering
  • Visibility modes

2. Abuse filter

Open upload is a spam magnet. Rate-limit by IP and account, detect malware or banned patterns, and require a challenge when volume spikes. Filters will be wrong sometimes, so keep an appeal or override path for trusted users. Do not wait for a human to review every paste before it is reachable if the product is 'instant share,' but do keep takedown fast.

Core concepts in this module

  • Rate limits
  • Content scanning
  • Takedown path
  • Challenge / CAPTCHA

3. Expiry sweeper

A background job lists pastes whose deadline has passed, removes metadata, and deletes objects. Because jobs lag, the read path must also compare now to expiry. Storage lifecycle policies catch blobs the sweeper missed. Log deletions so you can explain why a link died.

Core concepts in this module

  • TTL as policy
  • Read-time expiry
  • Lifecycle rules
  • Idempotent delete

4. Read cache and object storage

Popular pastes become hot keys. Cache the body and the metadata together so you do not serve a cached body after metadata says expired. Object storage holds the canonical bytes. Short pastes may live only in the database, but a single rule—'bodies in object storage'—is easier to operate once size grows.

Core concepts in this module

  • Read-heavy caching
  • Coupled cache keys
  • Object durability
  • Hot pastes

How the modules work together

A create call runs through abuse checks, stores the body under a random ID, and writes metadata with size, visibility, and expiry. A read loads metadata first. If the paste is expired or private, the service returns not found. Otherwise it serves from cache or storage and never executes the paste as HTML. A sweeper later deletes metadata and then the blob. Lifecycle rules on the bucket are a backup, not the only control.
