System Design: Yelp / nearby places

What this system is solving

Nearby search asks: what businesses around this point match a query, and which should appear first? Scanning every restaurant in the country is not an option. Geohashes and quadtrees bucket the map. Ranking then combines distance with review quality. The read path is heavy; writes to hours and reviews are eventually visible.

System blueprint

Cell boundaries miss edge results, so you always search neighbors. Distance alone is a poor ranking function.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Geo index

Geohash encodes a point into a string prefix that nearby points share. Quadtrees recursively split space where density is high. Either structure turns 'near me' into a few bucket lookups. You must query neighbors because a restaurant across the hash boundary is still next door. Split hot cells; do not keep a single 'downtown' bucket forever.

Core concepts in this module

  • Geohash
  • Quadtrees
  • Neighbor cells
  • Hot-cell splits

2. Ranker

Candidates are cheap; ranking is the product. Signals include distance, rating, review count, category match, and personal history. 'Open now' should be revalidated because hours change. Empty result sets should widen radius or relax filters rather than return a proud zero. Pagination uses a cursor over the ranked list.

Core concepts in this module

  • Distance + quality
  • Open-now recheck
  • Radius widening
  • Cursors

3. Reviews

Reviews are a write-heavy sidecar. They need moderation, spam detection, and an aggregate that can be recomputed. Do not average in place without remembering counts. Photos are objects on a CDN. A review is not a reason to rebuild the entire geo tree.

Core concepts in this module

  • Append reviews
  • Moderation
  • Recomputable aggregates
  • Async document update

4. Business documents and cache

The search document is denormalized: name, coords, category, coarse hours, rating. Details pages can be richer and more cached. When a business moves, both the document and the geo bucket change. Tombestone closed businesses so old deep links explain why a pin vanished.

Core concepts in this module

  • Denormalized docs
  • Details cache
  • Move / rebucket
  • Closed tombstones

How the modules work together

The API receives a point, radius, and text. Geo index returns business IDs in the covering cells plus neighbors. Ranker fetches documents, applies filters such as open-now (rechecked if stale), and sorts. The client then loads details and photos from cache. A new review updates the review store and eventually the document's average; it should not lock the geo index. Hot downtown cells are split so one partition does not own all of a city center.
