System Design: Slack / Discord

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Team chat is real-time fan-out plus durable history. People expect a message to appear in every open client and to still be there tomorrow after a laptop sleeps. Gateways hold WebSockets. A message service persists first, then publishes. Presence and typing are ephemeral so they do not drown the database.

System blueprint

If a client can reconnect and catch up from a sequence number, you can lose a gateway without losing the conversation.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. WebSocket gateway

Gateways terminate sockets, authenticate, and subscribe the connection to a set of channels. They should be stateless relative to message history. Shard connections by user so a person does not split events across machines without a plan. Heartbeats detect dead phones. This layer is where you apply per-connection backpressure.

Core concepts in this module

  • WebSockets
  • Connection sharding
  • Heartbeats
  • Slow-consumer handling

2. Message API and store

The API is the write authority: permissions, attachments, edits, deletes. Messages get a monotonic sequence per channel. Edits and deletes are new events against that ID so late subscribers converge. Search is a derived index, not the store itself. Large channels need pagination that is stable as new messages arrive.

Core concepts in this module

  • Per-channel sequence
  • Edit/delete events
  • Permissioned writes
  • Stable history pages

3. Channel router and pub/sub

Pub/sub carries live events to gateways. A channel with hundreds of thousands of members cannot be a single process doing a for-loop. Fan-out trees, partition the channel, or push to online members only and let others catch up. Membership changes must subscribe and unsubscribe gateways without dropping the persist step.

Core concepts in this module

  • Pub/sub fan-out
  • Online vs history
  • Membership updates
  • Partitioned channels

4. Presence and notifications

Typing indicators and online flags expire in seconds and should live in memory. Notifications go to devices that have no socket: push, email, or desktop. They must respect mute and mention rules. A notification is a derived event from a persisted message, so retries use the message ID.

Core concepts in this module

  • Ephemeral presence
  • Mute rules
  • Push fan-out
  • Derived notifications

How the modules work together

A send call persists a message with a channel sequence, then publishes to the bus. Gateways subscribed to that channel push to connected clients. Offline users get a notification. On reconnect, the client asks for messages after its last sequence. Slow clients are disconnected from live push and told to catch up in batch so one bad laptop does not stall the channel.
