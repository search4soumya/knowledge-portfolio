What this system is solving

Collaborative editing is a consistency problem. Two people type in the same paragraph and both expect their words to remain. Operational Transformation (OT) rewrites incoming operations against a server order. CRDTs encode merge rules in the data type so replicas converge. Presence cursors are ephemeral. Version history is a snapshot plus a log you can compact.

System blueprint

Pick a merge rule first. The websocket is just the transport for that rule.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Collaboration socket

This is a sticky session to a document shard so all live editors of a doc meet the same engine. On reconnect the client sends the last operation ID it applied. The socket should not be the database; if it dies, another instance must load the log. Authz is checked here: a viewer cannot submit edits.

Core concepts in this module

  • Sticky sessions
  • Reconnect cursors
  • Document sharding
  • Edit vs view

2. OT / CRDT engine

OT transforms an operation against concurrent ones so the server's order still preserves intent. CRDTs give each insert an identity so replicas can merge without a single transformer. Both need operation IDs and a story for undo. Choose one family and keep it; mixing ad hoc string patches will diverge. Large docs may split into blocks to keep transforms cheap.

Core concepts in this module

  • Operational transformation
  • CRDTs
  • Intent preservation
  • Block sharding

3. Presence

Cursors and selections expire when a socket goes quiet. They are broadcast but not written into the document history. Storing them durably would explode the version list and lie after a laptop sleeps. Color and name are display metadata on the session, not on the paragraph.

Core concepts in this module

  • Ephemeral cursors
  • Session metadata
  • TTL presence
  • No history pollution

4. Snapshotter and version store

The op log grows forever unless you checkpoint. A snapshot is a document state at a sequence. Older ops can be compacted after all clients are beyond them. Named versions are user-facing restore points. Compaction must not destroy legal evidence the product promised to keep.

Core concepts in this module

  • Checkpoints
  • Log compaction
  • Named versions
  • Restore

How the modules work together

An editor connects, loads a snapshot plus recent ops, and sends local operations. The engine assigns a sequence (OT) or merges a CRDT state, then broadcasts to others. Presence pings show cursors. Periodically the snapshotter writes a checkpoint so a new client does not replay years of keystrokes. Comments and suggestions are objects with their own IDs so they can ride the same session without breaking the text merge.
