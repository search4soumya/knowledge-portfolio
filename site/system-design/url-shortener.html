System Design: URL shortener

Beginner-friendly case studies that explain how familiar systems work, what they optimize, and where their designs fail.

What this system teaches

URL shortener is a useful case study because it turns a familiar product into a set of engineering decisions. Start with the user action, identify the data that must survive, and then decide which work can happen later.

  • Hashing — map long URLs to short keys
  • Key generation — avoid collisions
  • Key-value stores — serve redirects quickly
  • Analytics — record clicks asynchronously

How a request moves

A create request validates a destination and allocates a short key. The key and destination are stored. A redirect lookup reads the key from a cache or key-value store and returns an HTTP redirect; click events are sent to an analytics queue.

A beginner-friendly design

Use a unique random or sequence-based key, a primary key-value record, and a cache with expiry. Keep analytics out of the redirect path. If custom aliases are supported, reserve them transactionally.

Data, scale, and consistency

Keep the first version simple: separate the request path from background work, measure the slowest dependency, and store an identifier that makes retries safe. Add replicas and caches only after the access pattern is visible. Decide which values may be briefly stale and which action must be serialized, such as a payment or seat reservation.

What can go wrong

A hot link can overwhelm one cache entry, keys can collide, and malicious destinations can turn the service into a spam or phishing tool. Rate-limit creation, validate URLs, and make writes idempotent.

Key takeaway: The redirect path should do one tiny lookup; everything optional belongs off the critical path.
