System Design: URL shortener

What this system is solving

A shortener has two calls with opposite needs. Creating a link is a write with uniqueness and abuse checks. Opening a link is an extremely hot read that should be a single key lookup and a redirect. Analytics, preview pages, and custom aliases must stay off that redirect path unless you accept losing the performance that made the product useful.

System blueprint

The short key is the entire API. Generate it carefully, store it simply, and cache the hottest keys.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Key allocator

Keys can be random, hash-based, or issued from a counter encoded in base62. Random keys need enough bits to make collisions rare and a uniqueness check anyway. Hashing the destination makes the same URL collapse to one key, which may or may not be desired. Counters are simple but leak creation volume. Reserve custom aliases in the same transaction that writes the record.

Core concepts in this module

  • Key generation
  • Collision handling
  • Base62 encoding
  • Alias reservation

2. Redirect service and cache

This path should avoid joins, user profiles, and synchronous analytics. Read key, write a cache entry, return Location. Choose 301 if the mapping never changes, 302 if you need to keep seeing clicks at your edge. Signed or allow-listed destinations reduce phishing. A single viral key becomes a hot partition; replicate that entry widely instead of scaling the whole table.

Core concepts in this module

  • KV lookup
  • HTTP redirect semantics
  • Hot-key replication
  • Safety checks

3. Analytics

Clicks are a firehose. Drop them on a queue with the key, time, and coarse geography. Aggregate offline. If analytics is down, redirects should still work. Unique-click counts need a privacy-aware approximation, not a full replay of IP addresses in the request path.

Core concepts in this module

  • Async click events
  • Approximate counts
  • Privacy
  • Decoupled metrics

How the modules work together

A create request validates the destination, asks the allocator for a unique key, and writes the mapping. A redirect request hits the edge cache or the key-value store and returns 301 or 302. The click is appended to a queue for later counts. Custom aliases take a transactional reservation so two teams cannot claim the same word. If the cache is wrong, the store wins; if the store is down, fail the create, and decide explicitly whether redirects fail open from cache.
