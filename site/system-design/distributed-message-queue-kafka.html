System Design: Distributed message queue (Kafka)

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Kafka is a replicated, partitioned commit log. Producers append. Consumers read at their own offsets. Order is per partition, not global. Replication keeps the log alive when a broker dies. Consumer groups divide partitions among workers. Application correctness still depends on what you do when you crash after processing but before committing an offset.

System blueprint

Think 'distributed log,' not 'smart queue that deletes on read.' Retention is time or size, and replay is a feature.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Brokers and partition logs

A topic is split into partitions, each an ordered log on disk. Throughput scales with partitions, but a single key hashes to one partition. Retention lets consumers rewind. Disk layout and page cache are why sequential appends are fast. Choose partition count with future consumers in mind; shrinking is painful.

Core concepts in this module

  • Partitions
  • Append-only logs
  • Retention
  • Key hashing

2. Replication and controller

Each partition has a leader and followers. The in-sync replica set lists who is caught up. Acks=all means the leader waits for ISR. The controller assigns leaders when a broker dies. Replication is not a backup to object storage; it is how the cluster survives a node loss. Unclean leader election is a durability choice you should understand before enabling.

Core concepts in this module

  • Leader / followers
  • ISR
  • Ack modes
  • Controller failover

3. Group coordinator

A consumer group is a team sharing work. The coordinator assigns partitions so each partition has one active reader in the group. Rebalances pause work; cooperative protocols reduce that pause. Static membership helps rolling deploys. This module does not process messages; it decides who may.

Core concepts in this module

  • Consumer groups
  • Rebalance
  • Partition assignment
  • Static membership

4. Offsets

An offset is a bookmark. Commit too early and a crash loses messages. Commit too late and you reprocess. Exactly-once requires transactional producers or idempotent writes in the consumer. Lag is the distance between log end and committed offset; alert on time-to-drain, not only on a raw count.

Core concepts in this module

  • Offset commit
  • At-least-once
  • Idempotent consumers
  • Consumer lag

How the modules work together

A producer chooses a partition, usually by key, and waits for a configured ack. The leader broker appends and followers replicate. The controller manages leadership. Consumers in a group receive a partition assignment from the coordinator and commit offsets as they process. If a consumer dies, partitions rebalance. Hot keys pile onto one partition; that is a design mistake, not a broker bug.
