System Design: Twitter / X

What this system is solving

A social timeline looks simple: write a short post, then read a river of posts from people you follow. The hard part is the imbalance. Reads vastly outnumber writes, a few accounts have tens of millions of followers, and people expect a fresh feed in a few hundred milliseconds. The design therefore splits write work, read work, and search, and it treats celebrity fan-out as a special case.

System blueprint

The blueprint is a hybrid fan-out design. Ordinary posts are copied toward follower timelines at publish time. Very large accounts stay in a post store and are merged when someone opens the app. Search is a separate index, not a scan of the timeline cache.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. API gateway

Every mobile or web call lands here first. The gateway authenticates the session, applies per-user and per-IP limits, and routes writes to the tweet service and reads to timeline or search. It is also where you terminate TLS and attach a request ID. Keep this layer thin. If it starts composing timelines or talking to every store, one bad deploy can take the product down and you lose a clean place to shed load.

Core concepts in this module

  • Authentication
  • Rate limiting
  • Request routing
  • Load shedding

2. Tweet service

This is the source of truth for a post. It validates size and media, assigns a unique sortable ID, writes the post, and publishes an event. It does not walk millions of followers. That keeps the user-facing write fast and makes retries safe: the same client token should create one post, not two. Media binaries belong in object storage; this service stores only metadata and pointers.

Core concepts in this module

  • Write-ahead persistence
  • Unique IDs
  • Idempotent create
  • Event outbox

3. Fan-out workers

Workers consume the publish event and decide how to distribute it. For a typical account they push a lightweight reference into each follower's timeline cache. For an account with a huge audience they skip the copy and leave the post to be pulled later. This is the push-versus-pull decision. Workers must be able to pause, retry, and rebuild a slice of the graph without blocking the original writer.

Core concepts in this module

  • Timeline fan-out
  • Push vs pull
  • Backpressure
  • Partial rebuild

4. Timeline service

The home feed is a merge, not a dump of one list. The service reads cached entries for people you follow, adds recent posts from high-follower accounts, removes content you should not see, and pages with a cursor. Cursor pagination stays stable as new posts arrive; offset pagination does not. This module can be scaled by user shard because one person's feed does not need another person's cache.

Core concepts in this module

  • Read-time merge
  • Cursor pagination
  • Visibility filtering
  • User sharding

5. Search service

Search is a different product from the home feed. It needs an inverted index of terms, hashtags, and sometimes users. Indexing is asynchronous so a publish stays fast. Queries are served from replicas close to the reader. Do not reuse the timeline cache as a search engine; it is ordered by follow graph and time, not by term.

Core concepts in this module

  • Inverted index
  • Async indexing
  • Replica reads
  • Query ranking

6. Post store, follow graph, and caches

The post store keeps durable posts. The follow graph answers who should receive or see a post. The timeline cache makes the common home-feed read cheap. The search index makes term lookup cheap. Each store has a different consistency need: a missing cache entry is recoverable, a missing post write is not, and a stale follow edge can leak or hide content. Design expiry, rebuild, and authorization around those differences.

Core concepts in this module

  • Source of truth vs cache
  • Graph lookups
  • Cache invalidation
  • Hot-key handling

How the modules work together

A publish request is authenticated at the gateway, stored by the tweet service, and emitted as an event. Fan-out workers read the follow graph and write compact entries into timeline caches for ordinary followers. A home-timeline request asks the timeline service for those cached IDs, merges recent posts from a small celebrity set, filters deleted or muted content, and returns a cursor. Search never walks the cache; it queries its own inverted index. If a cache is missing, the timeline can be rebuilt from the post store and follow graph.
