System Design: Tinder

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

A dating app is geo-aware recommendation plus a tiny set of durable decisions: swipe left, swipe right, and match. Exact GPS should not be a product feature you leak. Candidates are generated in batches, filtered again at serve time, and swipes are append-only so a retry does not create two matches.

System blueprint

The stack you see is a recommendation. The swipe log is the contract. Matches are derived from two complementary likes.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Candidate generation

This module builds a stack using preferences, past swipes, and activity. It should run ahead of the user so swiping feels instant. Exclude already-swiped IDs. For a new user, fall back to popular or recently active profiles in the area. Generation can be approximate; the serve path filters again.

Core concepts in this module

  • Batch stacks
  • Negative filters
  • Cold start
  • Prefetch

2. Geo filter

People are indexed into cells. Query the current cell and neighbors, then widen. Do not return exact coordinates to the other user. Distance bands are enough. Travelers create a burst of writes; those should not explode a single city partition without overflow cells.

Core concepts in this module

  • Cell indexes
  • Neighbor queries
  • Privacy-preserving distance
  • Travel bursts

3. Swipe service

A swipe is unique on (from, to). Replay must not create a second like. Store direction and time. This log is also how you prevent showing the same person again. Rate-limit to reduce bots. The swipe service should not send chat messages; it emits an event if the like might complete a match.

Core concepts in this module

  • Idempotent swipes
  • Uniqueness constraint
  • Replay safety
  • Bot rate limits

4. Match service

A match exists when both sides liked. Create it once, open a conversation, and notify. Unmatching is a state change that should hide history according to policy. This module is small and must be correct; duplicate matches confuse billing and chat authorization.

Core concepts in this module

  • Mutual like
  • Exactly-once match
  • Conversation grant
  • Unmatch policy

How the modules work together

A session asks for a batch. Geo filter keeps people in a coarse radius and preference window. The client swipes. Each swipe is written once. When a like is mutual, match service creates a conversation thread and notifies both sides. Blocks and reports remove people from future batches immediately. Distance is computed from cells, not from a live share of street address.
