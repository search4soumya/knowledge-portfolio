System Design: Zoom / Google Meet

What this system is solving

A meeting is a latency-sensitive media graph. Signaling sets up the room. WebRTC moves audio and video. An SFU forwards streams without mixing every tile into one video, which scales better than an MCU that composites a single layout on the server. Quality is managed continuously through estimates of loss and bandwidth.

System blueprint

If you mix every participant into one server-side video, you pay encode cost on the server for every layout. An SFU forwards selected streams and lets the client decide what to decode.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Signaling and meeting control

Signaling exchanges join, leave, SDP offers, and ice candidates. Meeting control applies host policies: mute all, lock the room, admit from lobby. This path is not the video. It must be highly available, but its bandwidth is small. Store just enough session state to reconnect a client that refreshed the tab without creating a second ghost participant.

Core concepts in this module

  • WebRTC signaling
  • SDP / ICE
  • Room policy
  • Rejoin state

2. SFU media servers

A Selective Forwarding Unit receives each sender's stream and forwards it to subscribers. It can drop a video layer when a viewer has little bandwidth instead of transcoding a full MCU layout. Place SFUs regionally. Admission control matters: a 500-person webinar is a different topology from a 3-person standup. Monitor packet loss, jitter, and RTT per stream.

Core concepts in this module

  • SFU vs MCU
  • Simulcast / layers
  • Regional placement
  • Admission limits

3. TURN fallback

Some corporate networks block peer-to-peer. TURN relays media through a server you control. It is expensive, so it is a fallback, not the default. Health checks should prove that a client can reach at least one relay before you promise a meeting. Capacity here is a classic overflow pool.

Core concepts in this module

  • NAT traversal
  • Relay cost
  • Fallback only
  • Reachability checks

4. Recording and quality logs

Recording subscribes like a hidden participant or taps the SFU. Write media to object storage in chunks so a crash loses seconds, not the hour. Quality logs (loss, bitrate, device) are analytics and should never block sending the next packet. Compliance may require consent flags before this module is allowed to start.

Core concepts in this module

  • Recording as subscriber
  • Chunked storage
  • QoS telemetry
  • Consent

How the modules work together

A client joins through signaling, receives meeting credentials, and negotiates WebRTC with an SFU in a nearby region. Media packets flow to the SFU, which forwards them to other participants. TURN is used only when direct or peer-reflexive paths fail. Meeting control handles mute, lobby, and host actions as small messages. Recording is a separate subscriber so a recorder crash does not end the live call.
