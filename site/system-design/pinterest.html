System Design: Pinterest

Beginner-friendly case studies. Each page has a blueprint of the internal modules, an explanation of what every module owns, and the core concepts that module uses.

What this system is solving

Pinterest is a recommendation-heavy graph of users, boards, and pins. The home feed is not only 'people you follow.' It mixes that graph with related content and trends so a new account is not empty. Images are a CDN problem. Relationships and ranking features are a data problem.

System blueprint

Cold start is a first-class module. If the only source is the follow graph, day-one users bounce.

Modules in the blueprint

Each box above is a real responsibility. The notes below explain what that module owns, why it exists, and which ideas you should be able to name in an interview or design review.

1. Pin ingest

Ingest stores the image, extracts a signature for near-dup detection, and writes metadata. Scraped URLs need crawler politeness and spam checks. This pipeline is asynchronous so a save feels instant. The pin ID is the join key for graph edges and features.

Core concepts in this module

  • Media ingest
  • Near-dup signatures
  • Spam / crawl rules
  • Async enrichment

2. Graph

Users follow users and boards; pins belong to boards; pins can be related. These edges are candidate fuel. Store them in an access-oriented way: 'pins on this board,' 'followers of this board.' Unfollows and deletes must propagate so a private board does not keep leaking through a cached feed.

Core concepts in this module

  • User/board/pin edges
  • Access-oriented queries
  • Delete propagation
  • Privacy

3. Candidates and ranker

Candidates come from graph neighborhood, visual similarity, and popular topics. Each source should have a quota so one source cannot drown the feed. Ranking uses engagement and freshness. Offline jobs prepare most of this. Online, apply diversity rules so the feed is not twenty near-identical chairs.

Core concepts in this module

  • Multi-source recall
  • Source quotas
  • Diversity
  • Prepared features

4. Image CDN and feature store

Images are resized variants on a CDN. The feature store holds embeddings and counters the ranker needs. Features are versioned because a model trained on last month's schema should not silently read new columns. Evict features for deleted pins.

Core concepts in this module

  • Image variants
  • Feature versions
  • Embedding lookup
  • Deletion hygiene

How the modules work together

A save or upload creates a pin and edges to a board. Ingest extracts image features. Candidate generation reads follows, similar pins, and trends. The ranker orders a bounded set using the feature store. The home feed API pages with a cursor and rechecks that a pin still exists and is allowed. Images never travel through the ranker; the client fetches them from the CDN using keys on the pin.
