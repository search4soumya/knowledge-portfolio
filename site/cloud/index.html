Cloud Fundamental

Platform names change. The parts do not: a place to run, a place to store, a network, an identity, and a bill. These notes stay on that shared model.

The cloud model

A cloud provider runs large pools of machines, disks, and networks, and rents slices of them through an API. You stop ordering hardware for each new service. You start describing what you want, and you pay for what stays switched on.

Elasticity is the ability to add or remove capacity. Scalability is the ability of the design to handle growth at all. A single large virtual machine can be scaled up until it cannot. An elastic design adds copies and later removes them.

Places

A region is a group of data centers in a geography. An availability zone is an isolated group inside that region, with separate power and network. Putting two copies in one zone protects you from a bad deploy. Putting them in two zones protects you from a building. Putting them in two regions protects you from a region, and it costs more in latency, data transfer, and operational work.

The account, subscription, or project is the blast-radius boundary. Production and experiments should not share one. Bills, permissions, and quotas attach to that boundary.

Compute

Compute is anything that runs your code. The useful split is how long it lives and what you must patch.

  • Virtual machines look like servers. You choose the size, the image, and usually the operating system patches. They fit long-running processes, licensed software, and lift-and-shift.
  • Containers package a process and its dependencies. You still need something to run the containers: a service, or a cluster you operate. They fit when many services should share the same deployment shape.
  • Functions run for one event or request, then disappear. The provider patches the runtime. They fit irregular traffic and glue between services. They fit poorly when you need a long-held connection, local disk, or a cold start that breaks the latency budget.

Stateless compute is easier to scale. Put durable data in a store, not on the instance disk. An instance can disappear in a replacement, a scale-in, or a zone failure. If the only copy of a file lived there, it is gone.

Scale out by adding copies when the work can be split. Scale up by buying a bigger machine when the work cannot. Most "just make it bigger" stories end when the biggest size is still not enough.

Storage

Pick storage from the access pattern, not from the product name.

Three shapes, three jobs.
ShapeLooks likeGood for
BlockA disk attached to a machineDatabases and anything that expects a filesystem on one host
FileA shared filesystemSeveral machines reading the same tree
ObjectA key and a blob, reached over HTTPUploads, backups, images, data files, static sites

Object storage is durable because the provider keeps copies. It is not a POSIX disk, and it is not a database. You do not edit a byte in the middle. You write a new object.

A managed database is someone else's operational work: patching, backups, and often failover. You still own schema, indexes, query shape, and the decision about what the data means. Running the database yourself is reasonable when you need a specific version, extension, or placement. It is an ongoing job, not a checkbox.

Copies

Durability is "the provider did not lose the bits." Availability is "you can read them now." A backup is a separate copy you can restore, preferably in another region, with a tested restore. A replica that accepts the same bad write as the primary is not a backup.

Networking

A virtual network is your address space inside the provider. Subnets divide it. Routes and security rules decide what may talk. Private subnets have no direct route from the internet. Public ones do, and that should be a small set: load balancers and bastions, not every application server.

  • Load balancer. Spreads traffic across healthy copies and gives callers one address. Health checks must match real readiness, or the balancer will send users to a process that is up and useless.
  • DNS. Turns names into addresses. Use it for failover only when you have measured how long caches keep the old answer.
  • TLS. Protects the hop you terminate. Termination at the load balancer is common. Traffic behind it should still be restricted, and sometimes encrypted again, depending on who else shares the network.

Egress is easy to forget in the design and obvious on the bill. Data leaving a region, or leaving the provider toward the internet, is often priced differently from data staying inside. A chatty service that pulls from another region on every request will show up as cost before it shows up as latency you noticed.

Draw trust boundaries first: internet, your network, the data store, the management plane. Then place controls on the lines you actually cross.

Identity and access

Every call is made by someone or something. Users are people. Workloads are the programs: a virtual machine, a function, a pipeline. They should not share an account. A person leaving the team is not the same event as rotating what a service uses.

  • Grant the smallest permission that lets the job finish. Wide roles feel faster until a leaked key can do everything the admin can do.
  • Prefer short-lived credentials issued to the workload. Long-lived keys in a repository or a laptop are a common breach path.
  • Federate human login to one identity provider so joiners and leavers are handled in one place.
  • Separate the permission to change infrastructure from the permission to read production data.

Audit logs answer "who did what." Turn them on before you need them, and send them somewhere the same account cannot quietly delete. A trail that the attacker can erase is a diary, not evidence.

Identity is the real perimeter. Network rules still matter, but a valid key from anywhere will walk past a diagram that only shows firewalls.

Cost and responsibility

The shared responsibility model is the contract under the marketing. The provider secures the cloud: buildings, hardware, the hypervisor. You secure what you put in it: accounts, data, network exposure, and most configuration. On infrastructure as a service you patch the guest operating system. On functions the provider patches the platform, and you still own the code and the permissions it runs with.

Where money goes

  • Compute that is on while idle. Stop it, or size it to the real load.
  • Storage you forgot: old snapshots, unused disks, logs with no expiry.
  • Data transfer across regions and out to the internet.
  • Over-provisioned managed services left at their default size.

Tag resources with the system and the environment so a bill can be read. Set a budget alert before the month closes. A quota protects the account from a runaway loop. A budget alert tells a person.

Deleting an experiment is part of the design. If you cannot say who owns a resource, you cannot say whether it should still be running.
