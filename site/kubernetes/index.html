Kubernetes

Kubernetes keeps a cluster moving toward the state you declared. These notes cover the objects you actually write, and the habits that make a cluster operable.

Sections

The cluster picture

A Kubernetes cluster has a control plane and a set of worker nodes. You submit a desired state, usually as YAML: "three copies of this container, reachable under this name." Controllers watch the current state and try to close the gap. That loop is the product. SSH into a node is a debugging tool, not the way you make a change stick.

The API server is the front door. etcd stores the cluster data. Schedulers place pods onto nodes that have room. Kubelets on each node start the containers the scheduler assigned. You can run this yourself, or you can use a managed control plane and still own the workloads, the identity, and the network policy.

If a change is not in the manifest that Git holds, the next reconcile can erase it. The cluster is a mirror. The repository is the source.

Labels are the join key

Kubernetes does not wire objects by memory address. A Service selects pods by labels. A network rule selects pods by labels. Spend the time to make labels boring and consistent: application, component, environment. A typo in a selector looks like "the app is down" when the app is running and invisible.

Pods

A pod is the smallest thing you deploy. It is one or more containers that share a network namespace, which means they share localhost, and they can share volumes. Containers in a pod are started, scheduled, and die together. Most pods hold one application container. A second container is justified when it must share the pod's files or network: a proxy sidecar, or a helper that refreshes a certificate into a shared volume.

Pods are ephemeral. The disk inside the container goes away with the pod unless you mounted a volume. The pod IP changes when the pod is replaced. Callers should use a Service name, not a pod IP they happened to see.

Probes

  • Startup tells the kubelet the process is still booting, so a slow start is not mistaken for a deadlock.
  • Readiness tells the Service whether this pod should receive traffic. Fail it when a dependency you need is down.
  • Liveness restarts the container. Use it for a stuck process. Do not use it for a downed database, or the cluster will restart healthy code in a loop.

Requests and limits

A CPU or memory request is what the scheduler reserves. A limit is what the container is allowed to use. Without requests, the scheduler can pack a node until everything is slow. A memory limit that is too low kills the process. Set requests from a measurement, not from a guess you copy between services.

Workloads

You rarely create pods by hand. A workload controller creates them and replaces them when they disappear.

Choose the controller from identity and lifetime, not from habit.
ControllerUse when
DeploymentYou want N interchangeable copies. A rolling update replaces them. This is the default for stateless HTTP services.
StatefulSetEach replica needs a stable name, ordered startup, or its own disk. Databases and queues often land here, and they still need care that a YAML file does not supply.
DaemonSetEvery node (or a selected set) should run one copy: log collectors, network agents.
JobThe work should run to completion, then stop.
CronJobThe work should run on a schedule. Make the task safe to run twice, because a retry will.

A Deployment owns a ReplicaSet, which owns the pods. Roll back the Deployment, not a single pod. Deleting a pod is a restart. It is not a rollback, and it is not a fix for a bad image.

Horizontal scaling adds pods. It only helps when one request does not need more resources than a single pod has, and when sessions are not trapped on one copy.

Services and traffic

Every pod can reach every other pod by IP, across nodes. That flat network is convenient and it is also a wide default. Treat it as a starting point, then restrict it when the cluster holds more than one trust level.

A Service gives a stable name to a changing set of pods.
TypeWho can use it
ClusterIPOther workloads inside the cluster. This is the normal choice.
NodePortA port on every node. Useful for demos and odd network setups, noisy as a public design.
LoadBalancerAn external load balancer from the platform, with its own address.

HTTP routing sits above Services. An Ingress, or a Gateway, maps host names and paths to Services and often terminates TLS. The controller behind that object is a separate install. The Ingress resource does nothing until a controller is watching it.

Cluster DNS resolves Service names. Prefer name.namespace.svc.cluster.local in documentation, and the short name name only from callers in the same namespace. Cross-namespace calls should be explicit so a rename is visible.

NetworkPolicy is a lock you add once you know the allowed paths. An empty policy that selects nothing protects nothing. A policy that selects pods and lists no ingress denies them.

Configuration

Keep configuration out of the image. The same image should run in a test namespace and in production, with different config. Bake the build identity into the image. Inject the environment at deploy time.

  • ConfigMap holds plain settings: feature flags, addresses, small files. It is not secret, and it is not a place for a large binary.
  • Secret holds credentials and keys. The value is base64-encoded in the API, which is encoding, not encryption. Encryption at rest is a cluster setting. Anyone who can read Secrets in the namespace can use them.
  • Environment variables are easy and frozen at process start. Mounted files can be updated without a restart if the application re-reads them. Pick the one the process actually supports.

Do not store live Secrets in a public Git repository. A common pattern is to commit encrypted or referenced secrets, and let a controller materialize the Kubernetes Secret in the cluster. The manifest you review should not contain the raw password.

A ConfigMap change does not restart pods by itself. If the process only reads the environment at startup, roll the workload or the new value will sit unused.

Day-2 operations

The first deploy is the easy day. The cluster earns its cost on the days a node disappears, a rollout sticks, or a namespace runs out of memory.

Rollouts

A rolling update starts new pods before, or as, it stops old ones, depending on the surge and unavailable settings. Readiness must go green only when the new pod can serve. If readiness is always true, the rollout will happily replace a working version with a broken one. Keep the previous ReplicaSet so rollback is a declared change, not a scavenger hunt.

Namespaces and quotas

A namespace is a folder for names and a boundary for policy. It is not a strong security boundary by itself, but it is where you attach resource quotas, default limits, and who may deploy. Production and development on one cluster should at least be separate namespaces, with separate permissions. Many teams use separate clusters once the blast radius matters more than the extra cost.

What to look at

  • Events and pod status explain scheduling and crash loops.
  • Logs explain the process. Ship them off the node, because the node will be replaced.
  • Metrics explain saturation: CPU throttling, memory approaching the limit, restart counts.
  • A request id that crosses services explains a single failure better than a dashboard of averages.
kubectl is a window onto the API. Changes made only there will drift. Prefer a pull request that changes the manifest, then watch the controllers catch up.
