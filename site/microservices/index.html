Microservices

A microservice is a deployable boundary with its own data and its own reason to change. These notes stay on that boundary, not on a diagram full of boxes.

Sections

The boundary Owned data Contracts Calls between services Failure

The boundary

Split a system where the business already splits. Orders, catalog, and billing change for different reasons and are often owned by different people. That is a candidate boundary. A function that is merely "small" is not.

Each service should be deployable without a lockstep release of the others. If every change still needs three teams to ship on the same day, the split is only a network hop.

Start with a modular codebase and a clear data owner. Extract a service when independent deploy is the pain you are relieving.

Owned data

A service owns the tables it writes. Other services ask it, or subscribe to what it publishes. They do not share its database. A shared database hides the coupling until a column rename takes the neighbors down.

  • One writer for each fact.
  • Copies elsewhere are caches or projections, with a known delay.
  • A transaction that must update two services is a design smell. Put the rule in one service, or accept a process that can be retried.

Contracts

The contract is the request, the response, and the errors a caller can handle. Write it down. A breaking change is a new version, or a field that callers can ignore until they are ready.

Do not leak your tables through the API. Return the words the caller needs. Internal names can change without a coordinated release.

Calls between services

A synchronous call is simple and it couples availability. If the catalog is down, checkout waits. Use it when the caller cannot continue without the answer and the latency budget allows it.

An event is better when the receiver can act later. The publisher records that something happened. Consumers react, and they must tolerate duplicates and uncertain order. Name the event for the fact, not for the command you wish the other team would run.

Failure

The network will drop calls, and a dependency will be slow. Time out. Limit how many calls you pile up. Decide the fallback: a cached answer, a smaller feature, or a clear error. Retry only when the operation is safe to run twice.

Give every request an id that crosses services. A dashboard of averages will not tell you which checkout failed.
