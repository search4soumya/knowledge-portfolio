Architect Design Patterns

A pattern is a named way to arrange code when the same forces show up again. These notes separate object-level patterns from the styles that organize a whole system.

Sections

What a pattern is

A design pattern names a recurring problem, a structure that resolves it, and the consequences you accept. The name is the useful part. Once a team can say "this is a facade," the review can be about the trade-off instead of about redrawing the boxes.

A pattern is not a library, and it is not a rule. Copying the structure into a place that does not have the problem only adds types. The test is whether a reader can point at the force you removed: too many construction paths, a call site that knows every subtype, behavior that changes by mode.

Forces that sit under most patterns

  • Program to a small interface, not to a concrete type you do not own.
  • Prefer composition when inheritance would freeze a hierarchy too early.
  • Give a module one reason to change, and make the direction of dependencies obvious.
  • Keep the pattern at the boundary where the variation actually lives.
If you cannot name the force, you do not have a pattern yet. You have a drawing.

Creational patterns

Creational patterns matter when constructing an object is more interesting than using it. The caller wants a result. The variation is in which class is built, how many steps it takes, or how many instances should exist.

Use the pattern only when the construction cost is the problem.
PatternUse whenCost
Factory methodA subclass, or a strategy, should choose the concrete product.Another type in the hierarchy.
Abstract factoryYou must create a family of related objects that stay compatible.A wide interface that is painful to extend.
BuilderConstruction has many optional steps and an invalid half-built object would be dangerous.A second object whose only job is setup.
PrototypeA good instance already exists and copying it is cheaper or clearer than re-running setup.You must define what a copy means, including shared mutable state.
SingletonThe process truly has one shared instance, such as a process-wide clock in a tiny program.Hidden global state. Tests and reuse get harder.
A single instance created at the program edge and passed in is usually enough. Reach for a singleton only when passing the dependency is genuinely worse.

Structural patterns

Structural patterns describe how parts are composed so that a client talks to a shape it can live with. The client stays stable. The awkward collaborator is wrapped, hidden, or assembled.

  • Adapter converts one interface into another. Use it at the edge of code you do not control. Do not let the foreign type leak through the adapter.
  • Facade offers a narrow entry over a subsystem. It is a courtesy for callers, not a place to hide business rules that have no other home.
  • Decorator adds behavior around an object while keeping the same interface. Stacking many decorators makes the call path hard to see, so keep the stack short and named.
  • Proxy stands in for another object to control access, latency, or remote calls. A proxy that also changes meaning is an adapter in disguise.
  • Composite lets clients treat a leaf and a group the same way. It fits trees of UI, documents, and file-like structures. It fits poorly when leaves and groups do not share a real operation.

The shared risk is indirection. Each wrapper is a place a reader must open. Add one when it removes a dependency you do not want. Stop when the wrappers are the design.

Behavioral patterns

Behavioral patterns move responsibility for an action: who decides, who is told, and how a request is packaged. They are the right shelf when the object graph is fine and the collaboration is the mess.

Pick the pattern from the kind of change you expect.
PatternThe change you expect
StrategyThe same step must run one of several algorithms, chosen by the caller.
StateAllowed behavior depends on the mode of the object, and the mode changes over time.
ObserverSeveral parties need to hear that something happened, and the source should not know them.
CommandA request should be queued, logged, retried, or undone as a thing of its own.
Template methodThe skeleton of an algorithm is stable and a few steps vary by subtype.

Strategy and state look similar in code. Strategy is swapped in from outside. State changes because of what the object has already done. If you cannot say which one you mean, the design is still vague.

Observer is easy to add and hard to debug. Name the event, keep the payload small, and decide what happens when a listener fails.

Architectural styles

A style organizes the whole system. A pattern organizes a collaboration inside it. Mixing the two in one conversation makes both sound optional. They are not the same altitude.

Layered

Presentation, application, domain, and infrastructure sit in layers. Dependencies point toward the domain, not toward the database driver. The gain is a place for rules that are not HTTP and not SQL. The cost is pass-through code when a feature is a simple read.

Hexagonal, or ports and adapters

The application core defines ports: interfaces for the things it needs from the outside. Adapters implement those ports for a database, a queue, or a test double. The core does not import the framework. This is layered architecture with the dependency rule made explicit. Use it when you expect to test the core without the infrastructure, or to replace an adapter later.

Event-driven

Producers record that something happened. Consumers react. The coupling is through the event, not through a call that waits. You gain independent deploy and a natural audit. You pay with eventual consistency, uncertain order, and the need for idempotent consumers.

Pipes and filters

Each stage reads an input and writes an output. Stages can be reused and reordered when they do not share hidden state. It fits transforms and enrichment. It fits poorly when a later stage must reach back into an earlier one.

How to choose

Start from the pain, not from the catalog.

  1. Write the force in one sentence. "Callers know every storage class." "Construction can be left half done." "Behavior flips when the invoice is paid."
  2. Match the altitude. If the force is local, stay with a pattern. If the force is "the database is visible from the UI," you need a style.
  3. Name the cost you accept: more types, a delayed read, a harder stack trace, a copied event schema.
  4. Put the variation in one place. A strategy used once, with one implementation, is a function.
  5. Re-read the code a week later. If the pattern's name is the only way to understand a simple path, remove it.
A good choice is reversible. Hide the decision behind a small interface at the boundary, and keep the first implementation boring.
